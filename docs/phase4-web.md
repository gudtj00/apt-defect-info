## 만든 것 — 축① (단지별 담보책임기간 계산기)

브리핑의 축①(단지별 담보책임기간 계산기)을 실제로 동작하는 웹 화면으로 만들었다. 축③(건설사 명단)은 법적 리스크 때문에 변호사 검토 전까지 보류.

- **스택**: Next.js 16.2.10(App Router) + React 19.2.4 + TypeScript + Tailwind v4 + Drizzle ORM + SQLite(`better-sqlite3`) — 브리핑 지정 스택 그대로, sibling 프로젝트(portfolio-sub)와 버전 통일.
- **[lib/db/schema.ts](../lib/db/schema.ts)**: `complexes` 테이블. 브리핑 전체 스키마 중 축①에 필요한 부분만 우선 구현(kaptCode, slug, name, region, address, usedate, householdCount, builderName 등).
- **[pipeline/ingest_complexes.mjs](../pipeline/ingest_complexes.mjs)**: Phase 0에서 만든 에러 처리 로직(게이트웨이 에러 감지, 재시도, 동시성 3, 페이싱)을 그대로 재사용해서 실제 K-apt API로 단지 데이터를 SQLite에 적재. 현재 200건 적재됨(`npm run ingest:complexes -- 1000` 식으로 샘플 수 조절 가능).
- **[app/page.tsx](../app/page.tsx)**: 단지명/주소 검색 페이지.
- **[app/apt/[slug]/page.tsx](../app/apt/[slug]/page.tsx)**: 단지 상세 페이지. `lib/warranty-calc.ts` 엔진을 그대로 호출해서 공용부분(확정)/전유부분(추정)을 시각적으로 분리 표시하고, `lib/legal-constants.ts`의 `CALC_DISCLAIMER`를 하단에 고정 노출.

## 발견한 버그 — CommonMark 굵게 표시 깨짐

`content/defects/*.md` 5개 파일 모두에 `**N위, X.X%**를 차지한다` 같은 패턴이 있었는데, 실제 브라우저에서 `**...**`가 굵게 처리되지 않고 별표 문자 그대로 노출됐다. 원인은 CommonMark 이모파시스 규칙: 닫는 `**` 바로 앞이 `%`(구두점)이고 바로 뒤가 한글(공백도 구두점도 아님)이면, "닫는 델리미터"로 인정되지 않는다. 즉 한글 조사가 굵게 표시 바로 뒤에 붙는 문장 구조 자체가 CommonMark와 상성이 안 좋다 — 마크다운 렌더러(react-markdown) 버그가 아니라 스펙대로 동작한 것이었다. 굵게 표시를 포기하고 평문으로 바꿔서 해결했다(페이지 상단에 이미 빈도 배지가 따로 있어서 정보 손실은 없음).

## 하자유형사전 히어로 스플릿 레이아웃 (2026-08-06)

사용자가 PandaRank(pandarank.net)의 AI 숏폼 페이지 스크린샷(왼쪽 폰 목업+오른쪽 진한 색 블록 2단)을 보여주며 하자유형사전도 이런 식으로 표현하는 게 어떤지 물었다. 지금은 가운데 정렬 한 덩어리라 밋밋하다는 지적이었다. 색은 그대로 따라하지 말고 목적에 맞게 판단해달라고 했고, 실물 스크린샷이 없을 때 어떻게 하냐는 질문에 "실제 컴포넌트 마크업으로 만든 정적 목업"(사진이 아니라 우리 코드로 그린 가짜 화면 — 저작권 문제 없고 데이터도 진짜)을 제안해 승인받았다.

- **[app/defect/MockSearchPreview.tsx](../app/defect/MockSearchPreview.tsx)**: 브라우저 창처럼 보이는 틀(신호등 점 3개 + 가짜 주소창) 안에 실제 `DefectSearch` 컴포넌트와 같은 스타일로 검색창+결과 카드를 정적으로 그렸다. 내용은 지어내지 않고 `data/defect-types.json`의 실제 제34조(도배) 데이터를 그대로 옮겼다 — 쿼리 "벽지 들뜸"으로 검색하면 실제로 이 결과가 나온다.

- 브라우저로 실제 검색("누수" 입력 → 제10조 정상 반환)이 목업과 별개로 계속 작동하는 것, 두 패널의 그라디언트 색이 의도한 색상(초록 계열, 보라 계열)인 것을 JS로 계산된 스타일까지 확인했다. 콘솔 에러 없음, `npm run lint:legal`·`npx tsc --noEmit` 통과.

**재수정 1(같은 날)**: 사용자가 손그림으로 정확한 의도를 다시 보여줬다 — 왼쪽은 예시 화면 하나가 크게, 오른쪽은 위(증상으로 찾기)/아래(조문으로 찾기) 두 블록으로 나뉘는 구조였다(PandaRank 원본의 폰 목업+2단 컬러 블록을 그대로 재현하는 배치). 앞서 만든 "검색창 옆에 목업, 아래에 별도로 상위 2개 현상 컬러패널" 구성은 의도와 달라서 다시 짰다.

**재수정 2**: 그래도 "이게 아니다, 판다랭크처럼 화면 꽉 차게 하라니까"라는 피드백을 받았다 — `max-w-4xl mx-auto`로 가운데 정렬하고 `rounded-3xl border shadow-xl`로 카드처럼 감싼 게 원본과 다르다는 지적이었다. 원본은 좌우 블록이 브라우저 가장자리까지 꽉 차고(엣지투엣지), 세로로도 한 섹션이 꽤 크다. 그래서 바깥 wrapper(`max-w-*`, `rounded-3xl`, `border`, `shadow`)를 전부 없애고 `<section className="grid w-full md:grid-cols-2">`만 남겨서 실제로 화면 끝까지 채우게 했다 — 브라우저에서 JS로 실측(뷰포트 1440px일 때 섹션 폭 1425px, 왼쪽 오프셋 0px, 스크롤바 폭 감안하면 사실상 풀블리드)해서 확인했다.

**재수정 3**: 목업(`MockSearchPreview`)이 자꾸 논의의 초점이 되니, 아예 없애고 그 자리에 실제 콘텐츠를 넣자는 결정이 났다 — 왼쪽엔 (이전엔 히어로 아래 별도 섹션이었던) "현상별로 찾아보기" 6개 목록을 그대로 옮겨왔다. 최종 구조는 완전히 실제 기능 3개뿐이다: **왼쪽 = 현상별로 찾아보기**(연한 회색 배경, 6개 현상 목록), **오른쪽 위 = 증상으로 찾기**(진한 에메랄드, 실제 `DefectSearch` 입력 내장), **오른쪽 아래 = 조문으로 찾기**(바이올렛~푸시아 그라디언트, "전체 조문 목록 보기" 링크). 더 이상 쓰지 않는 `MockSearchPreview.tsx`는 완전히 삭제했다(다른 곳에서 참조 없음을 grep으로 확인 후 삭제). 히어로 아래 중복돼 있던 "현상별로 찾아보기" 섹션도 제거했다. 실제 검색이 진한 패널 안에서도 정상 작동("타일" 입력 → 제18조 반환)하는 것, 6개 현상 링크가 전부 정상 연결되는 것을 확인했다.

## 홈 검색 자동완성 + 홈/하자유형검색 UX 개선 (2026-08-06)

홈페이지 스크린샷을 보고 사용자가 4가지를 지적했다: ①하자유형검색의 "현상별로 찾아보기"가 밋밋하다 ②"하자 유형 사전" 명칭을 "하자 유형 검색"으로 전부 바꾸고, "증상으로 찾기"/"조문으로 찾기" 색이 별로다 ③홈 검색창이 좁고, 자동완성이 없다 ④검색 결과가 기능 아이콘 그리드보다 아래에 있다.

- **결과 위치**: 검색 결과 목록을 히어로 섹션 바로 다음(기능 아이콘 그리드보다 위)으로 옮겼다.
- **하자유형검색 패널 색 교체**: "증상으로 찾기"는 탁한 `emerald-900`(거의 검정에 가까운 녹색) 대신 밝고 선명한 `emerald-500→emerald-700` 그라디언트로, "조문으로 찾기"는 비비드한 `violet→fuchsia` 대신 차분한 `slate-800→slate-950` 무채색 다크 톤으로 바꿨다.

## PandaRank 참고 UI 개편 + 브랜드 컬러 전환 (2026-08-06)

사용자가 PandaRank(pandarank.net) 홈페이지 스크린샷을 주고 그 UI를 참고해서 만들되, 색은 지금 블루인데 목적에 맞는 색을 알아서 판단해달라고 했다.

**색 선택 — 블루 → 에메랄드**: 이 서비스의 핵심 가치는 "아직 유효한지(청구 가능=초록) / 곧 만료(주황) / 만료됨(회색)"을 확인하는 것인데, 브랜드색이 상태색과 무관한 블루였다. 에메랄드 계열로 바꾸면 "브랜드=아직 살아있다/유효하다"는 인상이 상태 배지의 초록과 자연스럽게 겹쳐서 강화된다고 판단했다. 그래서 `app/apt/[slug]/page.tsx`의 "청구 가능" 상태색(`#1a7f37`)도 브랜드색(`#059669`, emerald-600)으로 통일했다. `app/layout.tsx`·`app/page.tsx`·`app/defect/*`·`app/faq/page.tsx`·`app/globals.css`에 흩어져 있던 `blue-*`/`indigo-*`/관련 hex를 전부 emerald 계열로 교체했다(코드 리뷰용 최종 grep으로 브랜드색 잔여 blue 없음을 확인 — 아이콘 그리드의 장식용 하늘색 타일 하나는 의도적으로 남겨둠, 아래 참고).

**레이아웃 — PandaRank의 구조를 따온 것**:
- **네비게이션**: 로고 옆 점 + 텍스트 링크들 + 진한 톤(슬레이트) 보조 버튼("전체 조문 목록") + 브랜드색 CTA 버튼("담보책임기간 계산기") 2단 구성. PandaRank의 "광고/제휴 문의"(검정) + "로그인/가입"(초록) 조합과 같은 위계다.
- **검색 영역**: 원형 검색 버튼 + 카드형 검색창, 그 아래 "브랜드로 찾아보기" 퀵 태그(자이·래미안·힐스테이트·푸르지오·아이파크) — PandaRank의 인기 키워드 행과 같은 자리. 실제 존재하지 않는 "인기 검색어" 통계를 지어내지 않으려고, 흔한 아파트 브랜드명 5개로 대체했다.
- **프로모 카드**: 검색창 옆에 그라디언트 카드를 하나 배치해 하자 유형 사전으로 유도한다 — PandaRank의 오른쪽 광고 배너 자리를 자기 홍보 용도로 썼다.
- **기능 아이콘 그리드**: 검색 섹션 아래 4개 타일(계산기·하자유형사전·전체조문목록·FAQ)을 색이 다른 둥근 정사각형 아이콘으로 배치했다 — PandaRank의 8개 도구 아이콘 그리드를 이 서비스 규모(기능 4개)에 맞게 축소한 버전이다. 아이콘은 별도 라이브러리 없이 인라인 SVG로 직접 그렸다(패키지 추가 없이 가볍게 유지).

**검증**: 홈/하자유형사전/조문참조(제24조) 페이지를 브라우저로 열어 콘솔·서버 에러 없음을 확인했고, JS로 검색 버튼·로고 배경색이 더 이상 블루가 아님(랩 색공간 값의 a*가 음수·b*가 양수인 초록 계열)을 확인했다. `npm run lint:legal`·`npx tsc --noEmit` 통과.

## 검색 정규화 규칙 설계 및 반영 (2026-08-06)

전국 22,260개 단지 적재가 끝난 뒤(3차 배치 완료), 실제 데이터로 검색 실패 패턴을 먼저 조사한 다음 규칙을 설계했다 — 추측으로 규칙을 만들지 않기 위해서다.

**조사 결과 (전체 22,260건 기준)**:
- 단지명에 공백이 포함된 비율 **16.7%**(3,713건)인데 표기가 들쭉날쭉하다 — 같은 브랜드도 "더샵 리비테르 2차"처럼 띄어 쓰거나 "더샵리비테르1차"처럼 붙여 쓴다. 기존의 단순 `LIKE '%검색어%'`는 문자열을 있는 그대로 부분일치하므로, 사용자가 조금만 다르게 띄어 쓰면 실제로 존재하는 단지도 못 찾는다.
- 단지명에 **"아파트"가 포함된 비율은 33.6%**(7,486/22,260)뿐이다 — 나머지 66%는 이름에 "아파트"가 아예 없다(예: "동림우미", "고덕 온빛채"). "OO 아파트"처럼 검색하면 실제 이름에 "아파트"가 없는 단지는 찾을 수 없었다.

**반영한 규칙 2가지** ([lib/search.ts](../lib/search.ts)):
1. **공백 제거 후 비교** — SQL에서 `replace(lower(name), ' ', '')`로 이름·주소의 공백을 지운 뒤 비교한다. DB 컬럼에 정규화 필드를 추가하는 대신 쿼리 시점에 처리했다 — 2만여 건 규모에서는 인덱스 없이도 충분히 빠르고, 스키마 변경 없이 되돌리기 쉽다.
2. **토큰 단위 AND 매칭 + "아파트" 불용어 처리** — 검색어를 공백 기준으로 쪼개 각 토큰이 이름 또는 주소 어디에든 있으면 인정하고, 모든 토큰을 AND로 묶는다. 이때 "아파트"라는 토큰은 있어도 없어도 매칭에 영향을 주지 않게 걸러낸다(단, 검색어가 "아파트" 하나뿐이면 걸러내지 않고 그대로 써서 빈 조건이 되는 걸 막았다).

**검증**: curl로 실제 쿼리 결과를 확인했다 — "더샵 리비테르"(공백 있음)가 "더샵 리비테르 2차"·"더샵리비테르1차" 둘 다 찾아내는 것, "동림우미 아파트"(실제 이름엔 "아파트" 없음)가 정상적으로 "동림우미"를 찾아내는 것, "아파트"만 입력했을 때 전체 결과가 아니라 실제로 "아파트"가 들어간 이름만 걸러지는 것을 확인했다. 콘솔·서버 에러 없음, `npm run lint:legal`·`npx tsc --noEmit` 통과.

## 하자 유형 상세 페이지 톤·가독성 개편 (2026-08-05)

사용자가 상세 페이지(6개 프로즈 페이지 + 34개 조문 참조 페이지)를 클릭해서 읽어보고 5가지를 지적했다 — 말투가 딱딱하다, 설비/조문/원문요지 표가 줄바꿈 때문에 읽기 힘들고 따옴표가 거슬린다, 섹션 제목이 격식체다, 줄글이라 이해하기 힘드니 인포그래픽을 쓰라, "참고"가 본문과 안 구분된다. 다섯 다 한 번에 반영했다.

- **말투(~다체 → 습니다체)**: `content/defects/*.md` 6개 파일의 설명 문장과 `data/defect-types.json`의 `plainExplanation` 34개를 전부 "~습니다/~합니다" 체로 다시 썼다. 단, 법조문 원문 인용(블록쿼트)과 별표(공식 부속서) 표 안의 원문 전사는 그대로 뒀다 — 정부 원문 문구를 우리 말투로 바꿔 쓰면 왜곡이 되기 때문이다.
- **설비/조문/원문요지 표**: `globals.css`에 `table:has(th:nth-child(3):last-child)` CSS로 정확히 3열인 표는 앞 두 열(설비명·조문)을 `white-space:nowrap`으로 고정하고 마지막 열만 넓게 잡히도록 했다. 마크다운 자체에는 열 너비를 지정할 방법이 없어서 CSS `:has()` 선택자로 "3열 표"라는 패턴만 잡아 전역 적용했다 — 기능불량·들뜸및탈락·오염및변색 세 허브 페이지, 그리고 우연히 같은 모양인 균열·누수의 별표9·별표10에도 자동으로 적용된다. 원문요지 열을 감싸던 큰따옴표는 제거했다.
- **섹션 제목**: "1. 이게 하자인가" 같은 번호+질문 형식(사실상 시험문제/법조문 목차 톤)을 "이럴 때 하자로 봅니다"·"이렇게 확인합니다"·"보수비용은 이렇게 계산합니다" 같은 직접 안내형 문장으로 바꾸고, 번호는 텍스트에서 지운 뒤 `.defect-markdown h2::before`의 CSS 카운터(`counter(step)`)로 원형 배지를 자동으로 붙였다.
- **인포그래픽 — 발생빈도 막대 차트**: 6개 현상의 "N위, X%" 문장을 없애고, 6개를 한 번에 비교하는 가로 막대 차트 컴포넌트(`FrequencyChart`, [app/defect/[slug]/page.tsx](../app/defect/%5Bslug%5D/page.tsx))를 만들어 각 프로즈 페이지 상단에 배치했다. 현재 보고 있는 현상만 파란색으로 강조된다. 프론트매터의 `frequencyRank`/`frequencyShare`는 더 이상 안 써서 6개 파일에서 지웠다.
- **참고/비고 구분**: 중첩 블록쿼트(`> >`)로 쓰면 법조문 인용 블록쿼트와 다른 스타일(호박색 배경)이 적용되도록 CSS를 추가했다. "참고:"·"비고:" 문구를 전부 이 문법으로 옮기고 📌 표시를 붙였다.
- **인포그래픽 — 담보책임기간 표**: 기능불량·들뜸및탈락 페이지는 원래 "설비마다 다르다 — A(3년), B(2년)..." 식 줄글이었는데, 표로 바꿔서 스캔하기 쉽게 했다.
- 브라우저로 6개 프로즈 페이지 + 조문 참조 페이지(제37조)를 전부 열어 표 열 너비(JS로 셀 실측: 132px/88px/507px)와 참고박스 배경색(호박색 `rgb(255,251,235)` vs 인용 배경 `rgb(248,250,252)`)이 의도대로 적용된 것, CommonMark 굵게-표시 버그가 재발하지 않은 것(정규식으로 전 파일 검사)을 확인했다. 콘솔 에러 없음, `npm run lint:legal` 통과.

## 조문 참조 페이지(34개) 개편 — 나머지 조문도 같은 디자인으로, 보수비용 원문 노출 (2026-08-05)

위 개편은 프로즈 페이지 6개(누수·결로·균열·기능불량·들뜸및탈락·오염및변색)에만 적용됐었는데, `/defect/articles`(전체 조문 목록)에서 나머지 34개 조문(예: 제24조 조명설비)을 클릭하면 여전히 옛날 인라인 스타일 디자인이 나온다는 지적을 받았다. 세 가지를 고쳤다.

1. **디자인 통일**: `ArticleReferencePage`(`app/defect/[slug]/page.tsx`)를 인라인 style에서 Tailwind로 다시 쓰고, 프로즈 페이지와 같은 원형 스텝 배지(`StepHeading`)·법조문 인용 박스(`LawQuote`)·참고 콜아웃(`Callout`, 호박색)을 재사용하도록 만들었다. 34개 조문 페이지 전부 같은 룩앤필이 된다.
2. **뒤로가기 링크**: "← 하자 유형 사전으로"(`/defect`)가 아니라 "← 전체 조문 목록으로"(`/defect/articles`)로 바꿨다 — 이 페이지들은 전체 조문 목록에서 들어오는 경로이기 때문이다. (프로즈 페이지의 뒤로가기는 그대로 `/defect`를 가리킨다 — 그쪽은 인덱스 페이지의 "현상별로 찾아보기"에서 주로 들어온다.)
3. **보수비용 조문 원문 노출**: 지금까지는 "보수비용 산정: 제106조"처럼 조문 번호만 보여주고 끝이었다. `pipeline/extract_procedure_article_text.mjs`로 제45조~제124조(조사방법·보수비용 조문 80개) 전문을 `raw/law/` 원문에서 그대로 추출해 `data/procedure-article-text.json`을 새로 만들고, `lib/defects.ts`의 `getProcedureArticleTexts()`가 "제86조~제88조" 같은 범위 표기까지 파싱해서 해당하는 조문 전문을 전부 가져오도록 했다. 계산이 아니라 원문을 그대로 보여주는 것뿐이라 법적 리스크는 낮다고 판단했다. 추출 스크립트가 제84조·제45조에서 다음 장(章) 제목("제4장 하자보수비용 산정" 등)까지 같이 삼켜버리는 버그가 있어서, 장 제목 줄(`/^제\d+장/`)은 버퍼에 안 넣도록 고쳐서 재추출했다.
- 34개 조문의 `investigationArticle`/`repairCostArticle`이 전부 이 새 데이터에서 원문을 찾을 수 있는지 스크립트로 전수 검증(정상), 브라우저로 제24조(단일 조문 2개)·제26조(범위 조문 "제86조~제88조"가 86·87·88 세 블록으로 정확히 펼쳐짐 확인)·제44조(담보책임기간 없는 예외 케이스)를 직접 열어 확인했다. 콘솔 에러 없음, `npm run lint:legal`·`npx tsc --noEmit` 통과.
